# ADR 0007: Release pipeline: release-plz, dist, PyPI wheels and crates.io

## Status

Proposed.

## Context

Until now the only way to install `snow-rs` was `cargo install --git` or a source build: no tags,
no releases, no CHANGELOG, and `publish = false`. People who use the official `snow` usually
install it with `pip`/`pipx`, and many have no Rust toolchain. We want a release to take nothing
from the maintainer but merging a PR, and every release to reach three channels:

- GitHub Releases: prebuilt archives plus `curl | sh` and PowerShell installers;
- PyPI: `pipx install` / `uv tool install snowflake-cli-rs`;
- crates.io: `cargo install` / `cargo binstall snowflake-cli-rs`.

CI tests on Linux, macOS and Windows (the `test` matrix in `ci.yml`), so the binaries we ship for
those OSes are tested.

## Decision 1: one name, one binary

The package is `snowflake-cli-rs` on crates.io and PyPI; the binary stays `snow-rs`, so it never
clashes with the official `snow` on the same `PATH`.

## Decision 2: release-plz drives releases, with a fine-grained PAT

`release-plz.yml` runs on every push to `main`:

- `release-pr` opens or updates a release PR with the version bump and `CHANGELOG.md`, generated
  from Conventional Commits (documented in `CONTRIBUTING.md`, not linted).
- `release` publishes the crate to crates.io and pushes the `vX.Y.Z` tag, but only when the pushed
  commit is a merged release PR (`release_always = false`). Merging the release PR is the release.

Both jobs use the `RELEASE_PLZ_TOKEN` secret, a fine-grained PAT limited to this repository with
contents and pull requests read/write. A PR or tag created with the default `GITHUB_TOKEN` does not
trigger workflows, so the required `ci` check would never run on the release PR and the tag would
start neither release build. The workflow runs only on pushes to `main`, so no PR-triggered code
ever sees the secret.

Alternative: a manual `git tag && git push --tags` after merging a version-bump PR. No extra
secret, but every release needs a command from the maintainer. Rejected: release-plz turns a release
into a merge, which the maintainer already does.

A GitHub App token would work too and expire faster, but needs an App to create and maintain for one
repository; a fine-grained PAT is enough here.

## Decision 3: dist builds the binaries and owns the GitHub Release

The tag triggers `release.yml`, generated by `dist` from `dist-workspace.toml` (`dist generate`;
`dist plan` fails if the file is edited by hand, so change the config instead). It builds
`snowflake-cli-rs-<target>.tar.xz` (`.zip` on Windows) for:

| Target | Runner |
|---|---|
| `x86_64-unknown-linux-gnu` | `ubuntu-22.04` (glibc ≥ 2.35) |
| `aarch64-unknown-linux-gnu` | `ubuntu-22.04-arm` |
| `x86_64-apple-darwin` | `macos-15-intel` |
| `aarch64-apple-darwin` | `macos-15` |
| `x86_64-pc-windows-msvc` | `windows-2022` |

It also builds checksums, `snowflake-cli-rs-installer.sh` and `snowflake-cli-rs-installer.ps1`
(dist names installers after the package; there is no option to rename them), and creates the
GitHub Release with the CHANGELOG section as its notes. Release-plz's own GitHub release is off
(`git_release_enable = false`): two tools creating the release for one tag would race.

On pull requests `release.yml` only runs `dist plan`, with `GITHUB_TOKEN` and no secrets. That
catches a hand-edited or outdated `release.yml` before it reaches a tag.

`cargo binstall` reads `[package.metadata.binstall]` in `Cargo.toml`, which points at those
archives (tarballs hold a `<name>-<target>/` directory; dist's zips are flat).

No code signing or notarization: `curl | sh`, `pip` and `cargo` don't trigger Gatekeeper or
SmartScreen. No self-updater (`install-updater = false`).

## Decision 4: PyPI wheels with maturin `bindings = "bin"`

`pyproject.toml` uses the maturin backend with `bindings = "bin"`: the wheel only carries the
`snow-rs` executable. The version is dynamic, read from `Cargo.toml`, so it cannot drift from the
crate. The tag triggers `pypi.yml`, which builds wheels for manylinux and musllinux (x86_64,
aarch64), macOS (x86_64, aarch64) and Windows x86_64, plus an sdist, smoke-tests the wheels that can
run on their runner, and publishes them. Wheels build with the same `dist` profile (thin LTO) as the
archives.

## Decision 5: trusted publishing, one temporary token

- **PyPI**: trusted publishing (OIDC) from `pypi.yml`, job `publish`, environment `pypi`. PyPI
  accepts a *pending* publisher before the project exists, so no token is ever needed.
- **crates.io**: trusted publishing too, through `rust-lang/crates-io-auth-action`, but crates.io
  can only configure it on a crate that already exists. The first publish uses a temporary
  `CARGO_REGISTRY_TOKEN` secret. While that secret exists, the workflow uses it; once it is deleted,
  the workflow mints a short-lived token with OIDC instead, with no edit needed.

After the first release, `RELEASE_PLZ_TOKEN` is the only long-lived credential.

`id-token: write` is granted only to the two publishing jobs (`release` in `release-plz.yml`,
`publish` in `pypi.yml`); every workflow defaults to `contents: read`, except `release.yml`, which
needs `contents: write` to create the release. Third-party actions are pinned to major versions,
like `ci.yml`.

## Decision 6: the published crate

`include` in `Cargo.toml` ships only `src/**/*.rs`, `Cargo.toml`, `Cargo.lock`, `README.md`,
`LICENSE` and `NOTICE`: about 370 KiB compressed. Tests, goldens, fixtures, bench data, scripts and
docs (several MiB) stay in the repository. The packaged crate builds; its tests don't, since they
need those files. `rust-version` is the toolchain pinned in `rust-toolchain.toml`, the only one CI
builds and tests with. `homepage` is not set: Cargo warns that it is redundant when it equals
`repository`.

## Decision 7: the first release is v0.1.0

`Cargo.toml` is already at `0.1.0` and the crate is not on crates.io. For a package missing from
the registry, release-plz keeps the current version: the first release PR only adds
`CHANGELOG.md` for 0.1.0. Merging it publishes 0.1.0 to all three channels.

## Decision 8: a tag publishes only if its commit is on `main`

The tag workflows trust the tag, and PyPI's trusted publisher trusts the workflow file and
environment, not the ref. Without a check, anyone who can push a tag (an admin identity, an agent,
the `RELEASE_PLZ_TOKEN` PAT) could publish an unreviewed commit to PyPI and to the GitHub Release
the installers fetch, skipping the PR, `ci` and the maintainer's merge. crates.io is already gated:
it publishes from a push to `main`.

- `pypi.yml` starts with a `guard` job (full history, then
  `git merge-base --is-ancestor "$GITHUB_SHA" origin/main`). The build, sdist and publish jobs all
  need it.
- `release.yml` runs the same check as the first step of every `build-local-artifacts` job,
  injected by dist from `.github/release-guard.yml` (`github-build-setup` in
  `dist-workspace.toml`). `host`, which creates the GitHub Release, needs every build job to
  succeed, so nothing is released.
- A tag ruleset on `refs/tags/v*` (a host step) restricts updates and deletions, so a published
  release tag can't be moved to another commit.

Alternative: a custom dist `plan-jobs` reusable workflow. dist 0.34.0 renders its call as
`uses: $/.github/workflows/<name>.yml`, which GitHub and actionlint reject, so it can't be used.

## Consequences

- A release is: merge the release PR. Everything after that is automated.
- Commit messages and PR titles follow Conventional Commits, or the CHANGELOG lists them under
  "Other".
- None of this can run end to end before the first real release. `tests/it/release_config.rs`
  guards the decisions above (targets, installers, dynamic wheel version, a single GitHub Release,
  no secrets or `pull_request_target` on PRs, OIDC only on publishing jobs, the `main` check in both
  tag workflows).
- Upgrading dist means `dist init` with the new version and committing the regenerated
  `release.yml`.
